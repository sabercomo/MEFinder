# 整应用对齐内存验收：真实对齐的进程树峰值与任务后回落

2026-09-19：按当前"每任务一个计算进程"的生命周期，重测对齐的**整应用**内存曲线。结论：**一次真实冷对齐的整应用树峰值 1120–1383 MiB（5 个任务），全部落在任务级计算进程内；任务结束该进程消失，整应用回落到 30–86 MiB（回落占峰值 94–97%），连续 6 个任务（5 本不同书）无累积、无换页增量**。"计算时的瞬时峰值"仍是 1.1–1.4 GiB 量级，但本轮没有出现"必须处理"的证据：第四阶段（batch64→16）继续保留为候选，不阻塞第三阶段。

- 数据（公开摘要，无真实库 id）：[memory-app-alignment-2026-09-19.json](memory-app-alignment-2026-09-19.json)。逐样本时间线与私有标识在未跟踪的 `.codex-tmp/mem-app-real/{raw2.json,summary.json,run.log}`。
- 测量工具（本轮新增，纯测量、不改产品代码）：`scripts/mem_profile_app_alignment.py`。
- 被测代码：工作区 `codex/v0.5.5-integration`（`5af40cf`；6 任务系列跑到一半时并行落入 `cf8a7c2`，后端进程在该提交前已完成 import，故 `revision` 字段只标明提交窗口）。产品代码未被测量脚本改动。

## 0. 为什么要补这一测（口径）

[09-12 内存基线](memory-alignment-export-2026-09-12.md)量的是**任务本身**：当时对齐在主进程内计算，于是留下两条结论——任务后稳定驻留 571–704 MiB、每轮重加载模型的路径 +17–20 MiB/轮。2A/2C 之后计算改到独立子进程（[2C 报告](alignment-compute-runtime-2c-2026-09-15.md)），这两条结论需要按当前生命周期重测，且旧[四场景服务器基准](performance-real-4scenario-2026-09-13.md)的 1279–1314 MiB 峰值也是改动前测的。

本轮口径：

| 项 | 取值 |
|---|---|
| 被测对象 | `python -m me_finder serve` 起的后端进程＋它每任务生成的对齐计算进程。后端与桌面走同一装配路径（`web.make_handler` → `web_runtime.build_application_runtime`），差别只在桌面另注入 pywebview 原生能力钩子与 `app_data_root` |
| 采样 | 外部线程 psutil 20 ms 逐 pid RSS，16,120 样本 / 557.8 s；树值＝后端＋全部后代 |
| 驱动 | `POST /api/text-alignments/start` + `/status` 轮询（阅读器 UI 的真实路径），`force=true` |
| "回落"判据 | 任务后等 RSS 自然平稳（1 MiB 静默 2 s），**不调 `gc.collect`、不清缓存、不卸载模型** |
| 未计入 | pywebview 窗口 / WebView 进程（对齐路径不经过它）；见 §2 未验证项 |

工作负载是真实书库快照的**副本**：`.codex-tmp/real-library-20260911`（65 部 / 63,994 段）复制到隔离 runtime root，模型权重硬链接进 root、`document-vectors` 全新 → 首轮真算向量；MiniLM（`minilm-l12-v2`，默认档）。

- **身份核对**：pair A（德↔中）2047×1901 段 / 967 链接 / 795 接受 / 94 拒绝 / 78 未匹配 / 92 标题锚——与 [09-12 内存基线](memory-alignment-export-2026-09-12.md)记录的同一快照重复输出（967/795/94/78、92+30 锚）一致，故峰值量级可横向比较；其中 30 个 folio 锚不在本轮响应字段内，未比对。
- **偏差如实**：该快照 `index.sqlite3` 现值 sha256 为 `22809cc5…`，已不等于 09-11 冻结 manifest 的 `5670b0d1…`（后续被别的验收写过）。可比性只靠"同一对书 + 同一 counts"论证，不宣称字节级同基线。
- 另取 4 对真实书冷算（含 1 本 EPUB），全部单进程内连续投递。

## 1. 结果

单位 MiB。`树峰`＝整应用进程树峰值；`后端峰`＝仅后端进程；`worker 峰`＝该任务计算进程峰值；`任务后`＝settle 后的树驻留。

| # | 任务 | 耗时 s | 树峰 | 后端峰 | worker 峰 | 任务后 | 回落 | 链接 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 1 | pair A 德↔中 2047×1901 **冷** | 71.9 | 1126.1 | 75.1 | 1065.8 | 62.2 | −1063.8（94.5%） | 967 |
| 2 | 同对 **暖**（向量缓存复用） | 3.8 | 186.5 | 80.2 | 107.0 | 80.2 | −106.3 | 967 |
| 3 | 性别麻烦 中↔英 3018×3131 **冷** | 110.4 | **1382.5** | 85.6 | 1297.2 | 85.6 | −1296.9（93.8%） | 2430 |
| 4 | 消费社会 中↔法 3739×3404 **冷** | 166.4 | 1363.4 | 96.6 | 1266.9 | 58.2 | −1305.2（95.7%） | 1948 |
| 5 | 战斗美少女 中↔日 3601×3676 **冷** | 126.2 | 1120.5 | 73.4 | 1056.0 | 32.3 | −1088.2（97.1%） | 1799 |
| 6 | 动物化的后现代 中↔日(EPUB) 1499×1743 **冷** | 59.2 | 1212.9 | 47.0 | 1166.0 | 30.3 | −1182.6（97.5%） | 1221 |

任务前 idle 树驻留 **45.7 MiB**（一次真实搜索预热之后）；全部 6 个任务后 **存活计算进程 0 个**。

**已测量事实**

1. **峰值归属计算进程，不在应用进程。** 5 个冷任务 worker 峰值 1056–1297 MiB，而后端进程全程峰值 **≤96.6 MiB**（13 个 pid 里 1 个后端 + 每任务 2 个计算进程）。数值栈不进主进程，与 2C 主包精简的依赖归属一致。
2. **任务结束即回落。** 每轮 settle 后 worker RSS 归零、树驻留＝后端驻留 30.3–85.6 MiB；冷任务回落 1064–1305 MiB，占峰值 **94–97%**。机制在 `alignment_compute.py:548-551`（`finally` 里 `_terminate` + 清理 work dir）与 `alignment_compute.py:300-329`（POSIX 对整个进程组 SIGTERM，5 s 后 SIGKILL 并 `wait()` 回收）。
3. **连续任务无累积。** 驻留序列 62.2 → 80.2 → 85.6 → 58.2 → 32.3 → 30.3 MiB，斜率 **−15.3 MiB/轮**，末值**低于**任务前 idle 45.7 MiB。
4. **无换页压力。** 16 GiB 物理内存机器上，树峰占 6.8–8.4%；`available` 4813.7 → 5224.4 MiB（升），`swap used` 887.5 → 887.5 MiB（**未变**），`compressed` 0。
5. **形状与旧架构相同、绝对值随段数走。** 曲线是"0–15 s 内跳到 0.93–1.25 GiB（加载＋首批），随后缓慢爬升，进程退出瞬间归零"。段数最多的性别麻烦（6149 段）峰最高（1382.5），pair A（3948 段）1126.1。同一对 pair A 两次独立运行分别为 **1323.9 / 1126.1 MiB**（pilot 与本轮）——**跨进程/跨时刻绝对值散布在 ±200 MiB 级，只有形状和"峰值落在哪个进程"可作结论**。
6. **产品常态（缓存复用后再生成）便宜一个量级**：树峰 186.5 MiB、任务 3.8 s（对比冷算 1120–1383 MiB、60–166 s）。
7. **每任务恰好 2 个计算进程**：capability probe 21–23 MiB、存活 0.03–0.09 s；真算 worker 存活 57–164 s。probe 也起进程，但内存可忽略。

## 2. 判断（区分观察／推断／未验证）

- **观察（直接证据）**：09-12 的两条负面结论在当前生命周期**没有复现窗口**——模型内存随任务进程一起消失，所以既不存在"任务后 570–720 MiB 驻留"，也不存在"同进程内 +17 MiB/轮"。这是**结构性**切断，不是缓解：任务后 worker 数恒为 0、树驻留恒等于后端驻留。
- **观察**：唯一剩下的内存事实仍是**嵌入推理瞬时峰值 1.1–1.4 GiB**，量级与旧架构一致（同模型、同 batch64、同段数）。[batch 对照](batch-size-compare-2026-09-13.md)的 −258 MiB（−21%）收益针对的正是它。**本轮数据不改变"暂缓 batch16"的判断**：本机看不到换页、OOM 或累积，峰值只持续一分钟量级且随任务结束整体消失。是否开展仍取决于质量门槛与 `EMBEDDING_RUNTIME_VERSION` 决策，而不是内存曲线。
- **推断（弱，未做归因实验）**：后端驻留先升后降到 30 MiB，形状像 SQLite 页缓存/段落缓存的自然释放，与模型无关。
- **未验证（不外推）**：① Windows 与冻结包——本轮计算进程**回退到主解释器**（隔离 root 与本机 app 运行时都没有 `components/text-alignment/runtime/installed.json` 收据），装独立 uv 运行时后是另一个解释器路径，进程生命周期相同但未实测；② pywebview 壳 + WebView 进程的常驻内存未计入（桌面"整应用"严格口径还含它）；③ ≥10 本连续对齐、以及可用内存被压到 GiB 级以下的换页行为；④ e5-large 实验档（更大模型峰值必然更高，非默认路径）；⑤ 大书（>1 万段）单任务峰值，本轮最大 6149 段。

## 4. 复现

私有路径经 shell 变量传入，不写入报告/提交。

```bash
PY="$PWD/.venv-macos312-arm64/bin/python"
SNAP="$PWD/.codex-tmp/real-library-20260911"                 # 真实库快照目录（含 manifest.json）
MODELS="$HOME/Library/Application Support/MEFinder/runtime/components/text-alignment/models"
OUT="$PWD/.codex-tmp/mem-app-real"; mkdir -p "$OUT"

# 跨任务序列文件 $OUT/pairs.json：只读打开快照，从 document_groups + document_group_members
# 按 member_order 取前两本作为 (pivot, target)，写成
#   [{"title": "书名 zh-Hans3018xen3131", "document_group_id": …,
#     "pivot_source_file_id": …, "target_source_file_id": …}, …]
# 本轮取 性别麻烦 / 消费社会 / 战斗美少女的精神分析 / 动物化的后现代（pair A 不在其中，
# 它由 --manifest 的 alignment_request 提供，避免重复投同一对被判成暖路径）。

"$PY" scripts/mem_profile_app_alignment.py \
  --workdir "$OUT/root2" --db "$SNAP/index.sqlite3" --manifest "$SNAP/manifest.json" \
  --cross-series "$OUT/pairs.json" --models "$MODELS" --rounds 2 --task-timeout-s 1200 \
  --output "$OUT/raw2.json" --summary-output "$OUT/summary2.json"
```

`--synthetic` 可先用合成小对（360×240 段）冒烟测量链路：本轮实测 worker 峰 838.8 MiB、树峰 894.0 MiB、任务后 55.3 MiB、0 存活计算进程——**600 段的小对就已打到模型加载地板**，与 09-12 "400 段合成对即达 844.6 MiB、地板 ~843 MiB"一致。

隔离性：workdir 由脚本创建且拒绝非空复用，测量结束自动删除（含 3.2 GiB 库副本）；模型权重硬链接、`document-vectors` 全新；用户真实库（`data_root.txt` → OneDrive）未被打开。
