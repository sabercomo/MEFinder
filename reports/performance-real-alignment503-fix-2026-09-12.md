# 对齐 503 修复后的真实书库复测

2026-09-12：在本次固定交互负载的采样下，对齐期间重叠搜索 503 从 61/216（28.2%）降为 0/166；成功搜索结果与页码／字符锚点保持一致，12 个后台进程全部退出码 0。

**"消除 503" 的准确含义**：机制上不是让写入不再阻塞读，而是把"主动关闭只读引擎导致的即时不可读"改成"读者在 30s `busy_timeout` 内等待写者释放锁"。SQLite 锁的是整库文件——首次大书分段写入溢出 page cache 后会在提交前升级到持有 EXCLUSIVE，跨表读（搜索命中 `paragraphs`）在此期间被阻塞的是整段写入而非仅最后的提交。本样本里写锁都在 30s 窗口内清除，故 0 次 503；但这是**有界等待、非无条件保证**：默认 page cache 下首次大书若锁等待超过 30s 仍会向读者暴露为 503，该场景本轮未实测（列为 待验证，见 [议题记录](../docs/issues/search-unavailable-during-alignment.md)）。高频短词延迟是另一议题，本轮未处理。

## 修复内容

1. `TextAlignmentCoordinator._write_window` 不再在对齐的准备／发布两个写事务前后 `suspend()`/`reopen()` 共享搜索引擎（根因、机制与安全性分析见 [议题记录](../docs/issues/search-unavailable-during-alignment.md)）。`IndexRuntime` 自身的 suspend/reopen 语义、导入／删除／题录等写入路径不变。
2. 验证期间发现并归因了一例独立的上游退出崩溃（onnxruntime 1.29.0 内置遥测模块的原生上传线程在进程退出时 abort，崩溃报告 `Python-2026-09-12-174546.ips`，上游同族问题 [onnxruntime#24579](https://github.com/microsoft/onnxruntime/issues/24579)）。该线程由任何 ORT 会话创建而起，与修复无关，但它使正式协议无法稳定完成，且其 HTTP 上传路径与本地优先原则相悖；已在创建会话前调用 `onnxruntime.disable_telemetry_events()` 禁用（回归测试钉住顺序）。

## 方法与范围

沿用 [同日基线](performance-real-v0.5.4-2026-09-12.md) 的同一冻结快照 `.codex-tmp/real-library-20260911`、八条查询、解释器、模型与协议：65 部文献、63,994 段；三轮、每轮四场景、每查询至少五次，`--compare` 校验协议／语料／模型／环境一致。数据与模型复制到临时运行目录，未改用户库和已安装应用；测量期间未并行运行全量测试或构建。

被测基点 `fbe690b` 工作区（含本轮修复，`src/` SHA-256 `17aa7f26b306bd23…`），`valid=true`，`identity_mismatches=0`，各轮预热摘要一致。对齐成果计数逐轮完全一致：2,047/1,901 segments、967 links、795 accepted、94 rejected、78 unmatched、92 heading 锚、30 folio 锚。

## 实测结果

延迟仅计成功请求；并发场景仅计与实际任务重叠的请求。单位毫秒，RSS 为 OS 高水位 MiB。

| 场景 | 重叠请求 | 失败 | p50 | p95 | RSS | 启动 p50 | 退出 p50 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 普通搜索 | 0 | 0/120 | 71.9 | 4,850.7 | 91.8 | 445 | 182 |
| Markdown 导出期间 | 81 | 0/81 | 2,459.8 | 4,893.7 | 137.7 | 423 | 182 |
| EPUB 导出期间 | 88 | 0/88 | 2,427.5 | 4,935.8 | 139.0 | 456 | 146 |

对齐场景 HTTP 状态分布 `{200: 166}`，无其他错误、无超时；修复前为 61/216（28.2%），全部为快速 503。

## 与基线的比较及限制（必读）

- **503 计数（二值量）在本采样内可信，但不等于普适保证**：失败计数是二值量，本轮协议、快照、查询、模型、驱动均被 `--compare` 校验为与基线一致，故"本样本 0/166"这一观测不受下述延迟漂移影响。但如首段所述，它是"有界等待窗口内未超时"的结果，不能外推为"任意真实库、任意负载下都不会 503"——默认缓存下首次大书的锁等待时长未测（待验证）。
- **对齐任务耗时（区别于搜索延迟，归因待定）**：对齐首次计算任务从基线 96.8–103.4 秒变为 123.6–127.1 秒，复用任务从 3.2–3.4 秒变为 3.9–4.3 秒。本次复测结束后**同一时刻、旧代码**补跑了一轮对齐专项对照：首次计算同样为 123.6 秒（数据见诊断 JSON `.codex-tmp` 私有目录）。该事后单轮对照与本机连续数小时满载后疑似热节流的持续负载状态一致，但**一次非交错的旧代码补跑不足以排除本轮改动的性能回归**：负载漂移与回归会产生相似的均匀抬升，二者在此设计下无法区分。要下"是/不是回归"的结论，需在同一会话内**交错运行新旧代码**多轮对比。
- **搜索延迟（区别于任务耗时，归因待定）**：alignment 场景各查询成功搜索 p50 呈约 1.14–1.20 倍的均匀抬升；同批 normal 场景高频「社会」p50 反而略快于基线（≈4.8s 对 ≈4.9s）。该逐查询延迟比值既不可解读为修复引入的延迟成本，也不可据此排除该成本；normal／导出场景的 p50 变化同样受采样构成与上述漂移影响，均不作为结论。当前证据只支持："本样本未观察到 503；对齐期间搜索延迟与对齐任务耗时较基线均升高约 +15%~+25%，归因待定。"
- 对齐期间重叠请求数从 216 降为 166：搜索不再快速失败、每次成功请求在漂移下耗时更长，顺序客户端单位时间内发出的请求随之减少，分母因此不可直接比较。
- 每轮两个对齐任务（一次真实计算 + 一次 `force=true` 向量复用）与基线结构一致。

## 结论

在本次固定负载采样下，正常对齐操作引起的搜索 503 未再出现：重叠搜索全部 200，结果身份与锚点摘要与预热一致，任务后搜索恢复校验通过，全部进程以退出码 0 结束。机制是把"关引擎导致的即时不可读"改为"在 30s busy_timeout 内的有界等待"，因此该结论限于写锁在窗口内清除的情形；默认 page cache 下首次大书的实际锁等待时长未测（待验证），不能外推为普适无 503 保证。计算工作进程的触发条件（写窗口收窄后 503 率仍 >5%）在本样本未触发，0.5.4 维持进程内对齐生成。

延迟方面需区分两个量且均归因待定：**搜索延迟**（各查询成功搜索 p50）与**对齐任务耗时**（首次计算/复用秒数）本轮较基线均升高约 +15%~+25%，但一次非交错的旧代码补跑无法区分负载漂移与性能回归，须交错新旧代码复测后再定。这不改变"本样本 0/166"这一二值观测。
