# 启动与结构化阅读延迟复审

2026-09-19：已复现并修复源码中的首屏排队路径；本机安装包构建结果在文末单列。不以接口耗时冒充完整桌面冷启动耗时。

## 已确认的原因

- GLM 已修复自动匹配滑杆程序性回填派发 input 导致递归写偏好的路径；本轮只读核对 `/Applications/MEFinder.app` 静态资源，安装版确实已含该修复及 1.2 秒延迟预取。
- 但完整 overview 仍逐对读取 alignment_links / alignment_link_members，计算匹配比例与待检查数。真实书库快照副本（8 作品、17 版本对、656325 条链接、1608118 条成员）首次 cProfile 3.136 秒，其中 3.123 秒在 `_direct_run_statistics`。
- 服务器是 `ManagedThreadingHTTPServer`，不是单线程。排队来自 `IndexRuntime.run_when_ready` 在执行整个 overview 时持有 `_state_lock`；文献库和结构化正文同样需要该锁。锁保证索引替换安全，本轮保留它。
- 原阅读器每次打开都先调用全库 overview，再发正文请求。即便只阅读一本书，也会等待全库详细统计。延迟预取与前端已加载缓存不能解决这个首次请求及阅读器路径。

## 最小修复

- overview 增加 `include_statistics=0`，只查询作品、语言、版本对及直接/间接/失效状态，不读链接统计；无参数请求保持原有完整响应。
- `source_id` 限定所在作品，`source_id + target_id` 限定版本对。阅读器只读取当前作品的轻量状态。
- 启动立即读取轻量状态，去掉固定 1.2 秒延迟与重复可用性读取。文献库摘要先显示，作品标签随后补齐。
- 正文请求完成后才加载阅读器作品上下文和对齐目标，正文不等待这些附属信息。
- 作品页只在显示直接对齐的统计时请求该版本对。保留精确统计算法，错误可见并能重试；旧响应不能覆盖失效后的对象。阅读器返回时轻量刷新，丢弃可能已被人工校正或新对齐改变的统计。
- 不改数据库 schema、索引锁、对齐算法或 batch64；不用永久缓存掩盖慢请求。

## HTTP 诊断结果

使用同一隔离 serve、同一书库快照，先发 overview，30ms 后发第二个请求；完整响应 SHA-256 比较见 [JSON](startup-reader-latency-2026-09-19.json)。

| 场景 | 完整统计 overview 在先 | 轻量状态 overview 在先 |
|---|---:|---:|
| 文献库摘要 | 3250.67 ms | 58.14 ms |
| 结构化正文（60 页） | 2165.01 ms | 24.26 ms |
| 对应 overview（文献库轮） | 3138.30 ms | 2.94 ms |
| 对应 overview（正文轮） | 2164.60 ms | 2.69 ms |

- 两轮中文献库、正文的完整响应分别逐字节相同；不是删减阅读内容换取速度。
- 完整 overview 与修复前 JSON 深度相等；轻量 overview 仅省略匹配比例和待检查数（保留字段为 null），其余内容相同。
- 当前作品的轻量状态 HTTP 请求 2.31ms；单独正文 36.06ms。首屏不再主动启动任何全库详细统计。
- **限制**：这是排队机制诊断，不是隔离系统负载的多轮性能基准。期间另有独立内存测量任务及后续构建，冷暖缓存未控制；不据此承诺固定倍率或所有机器的启动时间。完整统计本身仍可能耗时，但不再用于首屏与阅读器。
