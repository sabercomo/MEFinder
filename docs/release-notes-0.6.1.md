# MEFinder 0.6.1（开发中）

## 开发维护

- 修正 SQL 架构检查误报：按文件与完整调用目标排除已核实的搜索服务、解析执行器调用，不再把四个应用服务模块计为数据库查询模块。
- 将 persistence 之外的 SQL 棘轮从文件集合改为逐文件调用数量；已有模块增加 SQL 与新增 SQL 模块均会触发门禁。首次校准为 10 个文件、72 处调用，后续搜索查询迁移后收紧为 8 个文件、68 处，含解析任务账本的 schema 与事务语句。
- 新增隔离源码树回归测试，覆盖服务与 SQL 混合调用、动态查询、游标、批量执行、未知执行器以及现有模块内增加调用等情况。
- 运行时版本、MCP 契约 release、HTTP 契约快照、Windows 冒烟工作流和相关测试同步到 0.6.1；HTTP 路由与 MCP 工具接口未变。版本展示使前端装配摘要变化，字节数保持不变。
- 搜索精确/标准化、忽略空格/标点的候选查询与上下文查询统一归入持久化层，保留原连接、流式读取、候选预算和查询计划；评分、页码和字符定位规则保持不变。
- PDF 提取拆分为导入协调、原生解析、段落及锚点构造三项职责；保留旧导入入口，新增完整输出快照和单向依赖守卫。
- 新增 `errors.UserFacingError` 表示“消息可直接给用户看的预期错误”，`MinerUError` 改为它的子类。备份、删除、导入任务、页码映射、各 controller、CLI 与 web 装配等 21 个与 MinerU 无关的文件不再借用 `MinerUError`；仍导入它的只剩 5 个 MinerU 解析相关文件，并由守卫钉住。捕获范围与 HTTP 状态码、错误文案保持不变。
- 跨模块共用的 96 个私有辅助函数/常量/类改为公开名（另 2 个本已公开、只是被私有别名转手），使用方一律从定义模块直接导入，不再经 `text_alignment`、`database` 等旧模块转手；跨模块私有导入从 152 处降为 0，并新增守卫禁止回潮。只改名称与导入路径，函数逻辑未改。
- 三个组件安装器（MinerU 本地版、译本对齐运行时、本地 OCR）重复实现的 uv 下载日志解析、测速与剩余时间、分块写盘、SHA-256 校验、uv 解包发布和子进程停止，收进新的 `component_install.py`，各安装器只保留清单、状态、重试策略与安装步骤。各组件显示的下载速度与剩余时间算法保持原样。
- 解析任务账本 `large_document/job_ledger.py` 确认为“一个模块独占一个自带 schema 的数据库”（`data/parser_jobs.sqlite3`），不搬进 `persistence/`（搬过去会引入 `persistence/` 禁止的上行 import）。SQL 棘轮改为两张表：待收口的散落 SQL 从 8 个文件 68 处收紧为 7 个文件 25 处，账本的 43 处登记为已核实例外，并由单一 SQL 执行者、单一 schema 所有者、外部只读走 persistence 三条守卫钉住；例外表同样只许减不许增。
- 循环依赖守卫补齐导入解析：此前 `from . import native as pdf_native` 这类写法的目标被记成父包（顶层模块直接丢掉），`from ..persistence import translation_work_reads` 这类“被 import 的名字本身是子模块”的写法同样失准。补上后包内相对边由 726 条（其中 11 条指向并不存在的模块）变为 721 条真实边，含 6 条此前不可见的依赖；按完整解析重扫，包内循环依赖仍为 0。这是补将来会漏报的口子，不是修现存 bug。
- 检索层删除 JSON 索引后端，只剩 SQLite 一条路。`data/index.json` 保持为纯导出格式（CLI 的 `--export-json` 才写，SQLite 一律构建），`load_index` 与备份保留；`SearchEngine` 拿到非 SQLite 后缀的索引改为明确报错，传 `data/index.json` 时仍重定向到 SQLite 库。删除 `search/recall_memory.py` 与四个模块里的 8 处后端分支，`search/` 包由 2,971 行降为 2,693 行。产品入口一律传 SQLite 路径，无可观察差异。
- 三个组件安装器的取消与关停路径收口：关停（取消全部 → 停子进程 → join 工作线程）与取消请求由两份合为一份，取消检查、取消感知等待、轮询循环里的"先收子进程再抛"、清单路径解析、删目录各由三份或两份合为一份，九处硬编码的取消文案收成两个常量，全部加进已有的 `components/install.py`。各安装器的清单、状态模型、重试策略、`_run_command`、测速算法与安装步骤不变；对齐运行时的 `close()` 与 strict 删目录结构本就不同，登记为例外。四个文件总行数由 4,616 增至 4,714——共用件带 Protocol 与 docstring，比它替掉的内联重复更长，收益在"改一个功能牵动几处"而不在行数。
- `src/me_finder/` 顶层 87 个模块按领域移入 `alignment/`、`bibliographic/`、`components/`、`export/`、`parsers/`、`pdf/`、`search/` 七个子包，顶层由 163 个文件降为 76 个；导入、测试替换点、对齐计算进程的启动模块与打包常量同步改写，不保留旧路径转发。命令行与 MCP 入口（`src.me_finder.mcp_server`）位置不变。

## 范围与限制

本轮完成架构评估的三项局部整理、2026-10-31 评估的全部七项，以及收尾后对安装器取消/关停路径的收口，不调整检索算法、页码策略或 schema，也不重解析用户文献库。唯一可观察差异：导入索引失败、文档包导入失败、PDF 页内文字刷新失败这 3 处提示会带上异常类名；若失败原因是已迁移的通用错误，类名由 `MinerUError` 变为 `UserFacingError`。静态检查采用已核实目标的精确豁免，不做 Python 类型推断；未知的 `execute*` 调用仍计入棘轮，需审阅后确认归属。

既有 0.6.0 发布说明和安装包保持不变；0.6.1 尚未打包、安装或发布。
