# v0.5.8 迭代说明

## MCP：让 Agent 少试探的只读查询

工具数 13 → 15，全部新增能力只读，不新增写工具，不运行自动检测，不读源文件。

- 新增 `describe_page_mapping`：按连续区间说明一篇文献哪些位置有可引用页码、映射方法与印刷页码起止；PDF 一页对一页的区间给出偏移（印刷页码 = PDF 页号 + offset），区间之间偏移变化即书中换档，双开页等非一页对一页区间不给偏移。判定与检索、阅读结果共用 `page_display.resolve_citation_page`，未校准区间如实标 `uncalibrated`，不推算。
- 新增 `list_sections`：列出与阅读器目录同源的一、二级章节及位置范围；没有可识别标题时返回空列表，不猜章节边界。
- `read_document_window` 新增可选 `section_index`：只读该章节，窗口不越过章节终点，`section.next_start` 用于续读；不传时行为不变。
- `list_documents` 每篇文献新增 `work`：所属作品、是否基准版本，以及组内其他版本是否已与本篇对齐（即 `find_parallel_passages` 能否返回对照）。读取不会为旧库补建作品组表。
- `verify_quotes` 的每个命中新增 `section`（章节标题路径），用于发现“逐字命中但语境不对”的引用；`locate_quote` / `diff_quote` 输出不变。
- 代价：模型可见工具上下文 41,385 → 49,480 字节（+19.6%），见 `docs/mcp-v1-quality-report.md` 2026-09-29 补充。

## MCP：AI 书目补全（经用户确认）

工具数 15 → 17，新增两个带确认门槛的写工具。

- `propose_bibliographic_update`：AI 从原书版权页等读出题录后提议补全，每个字段必须附原书依据原文，可附页码。逐字段预览 fill / same / conflict：只填空字段，已有值即使不同也不覆盖；只记录待确认请求并返回一次性确认码，不改任何题录。
- `confirm_bibliographic_update`：用户明确同意后确认。MCP 进程不写导入配置（其锁只在桌面进程内有效，跨进程写会与导入/保存互相覆盖）；由桌面端后台每 5 秒取已确认请求，走人工保存同一流程写入配置与索引，并在保存锁内按最新题录重新判定只填空字段，用户同时编辑的值不会被覆盖。桌面端未运行时，下次启动写入。
- 写入结果（applied / failed、已填字段、冲突保留的原值）经 `read_bibliographic_metadata.update_requests` 可查。面板来源显示「人工维护」，字段证据记为 `mcp_agent` 并带依据页码与原文。
- 数据库 schema v8 → v9：新增 `bibliographic_update_requests` 表（迁移为纯加法；全量重建时随快照保留）。v9 库不能再被 0.5.7 及更早版本打开。
- 模型可见工具上下文 49,480 → 54,174 字节。

## 检索：两字短词提速

- 两字及以下的查询（如"社会""麒麟"）原来要全表扫描。默认开启繁简联合时，稀有的繁体写法拖慢整个请求：真实库副本上"社会"约 2.7 s，无命中的"黠慧"约 8 s。
- 新增"单字 + 相邻两字"辅助索引，只用来缩小候选范围，匹配判定、逐写法候选预算、排序、高亮、页码锚点都不变。真实库副本上 30 组查询的完整响应与此前逐字段一致；两字词请求降到约 1～22 ms，fuzzy 模式下"麒麟"从约 9 s 降到约 0.2 s。三字以上的查询不变。
- 数据库 schema v9 → v10：纯加法迁移，只建表和触发器，并把现有段落登记为待补索引。桌面端启动后在后台分小批补完（6.4 万段的库约 2 分钟，单批写锁 ≤ 0.22 s）；补完之前自动走原来的扫描，结果不受影响。导入、删除、重建都由触发器自动登记，不会漏。库增加约 90 MB。v10 库不能再被更早版本打开。
- 数据库 schema v10 → v11：只替换三个触发器，改为只登记待补、不再直接删辅助索引里的旧词元（旧词元由后台补索引时清掉）。原因见下条。v11 库不能再被更早版本打开。
- SQLite 版本：打包的桌面端与 MCP 侧车统一要求 SQLite 3.43 及以上，三个构建脚本在空库里查不到辅助索引表就中止打包；Windows 两脚本还在 PyInstaller 启动前，用实际打包解释器（`PackagerPythonExe`）执行建表能力探测，避免测试解释器与打包解释器不同时漏检。从源码在更旧的 SQLite 上运行时：自动保持原来的扫描，而且即使这个库已经在别的机器上建好辅助索引，也能正常搜索、导入、删除和修改（复验在 SQLite 3.42 上发现 v10 触发器会让段落更新/删除报 `unrecognized option: "contentless_delete"`，v11 已修）；这些改动会登记为待补，回到 3.43+ 时自动补齐。
- 旧 SQLite 上首次建库时没有辅助索引，即使库已是当前 schema，换到支持的运行环境后，桌面后台也会自动补装并分批建立索引；已有索引与待补进度保留，无需重建文献库或再次升级 schema。
- 模糊搜索（两字以下）在截断到前 64 个候选之前，同分候选改按“文献、段落序号”排序，不再依赖查询计划的读取顺序（复验发现执行过 `ANALYZE` 且物理顺序与段落顺序不同时，开关辅助索引会得到不同首条）。全库模糊搜索在同分候选超过 64 个时，入选哪些段落可能与之前不同。
- `search_passages`（主题检索）此前对两字查询在 SQLite 库上一律返回空：短于三字建不出 FTS 查询，回退分支只扫描内存段落表，而 SQLite 后端从不加载它（“社会”查不到而“社会学”能查到）。改为直接查库并复用模糊搜索已有的短词预筛；书目类型、单本文献、作品组范围照旧生效，有无预筛的返回逐字段一致，三字以上仍走 BM25 全文索引。先写复现测试 `tests/test_search_passages_short_query.py`（修复前按预期失败）。
- 架构：`search_passages` 的召回与排序拆出 `search_recall_passages.py`，它的两条读查询、以及召回级联共用的范围谓词，下沉到 `persistence/passage_reads.py` 与 `persistence/paragraph_scope.py`；「`persistence/` 之外不新增执行 SQL 的模块」这条门禁未放宽，`search_recall.py` 的行数上限随之从 580 降到 477。
- 已知遗留：fuzzy 模式下搜常见短词仍慢，候选遍历与原文字符位置映射需要分段测量，不能一律归因于相似度打分；两字候选含完整查询时评分函数会直接返回。
- 已知遗留：主题检索的两字查询只切出一个两字片段，每条命中重合度相同，SQLite 按文献、段落序号和段落 ID 排列；旧内存后端同分时保留输入次序，两者不保证同序。单字查询通常无法召回长段落，但归一化整段恰好等于该单字时可以命中。短词要不要放宽召回，等召回与噪音一起量的基准出来再定，见 `docs/issues/search-short-query-followups.md`。
- 复审补强 `search_passages` 测试：在辅助索引真正建好后核对预筛开关完整响应一致，再覆盖更新/删除待补与 64/65 候选截断边界；原测试仅覆盖全部待补，现已用破坏预筛的实验验证新测试能检出问题，产品查询代码保持不变。
- `search_passages` 两字查询提速：命中段落先按重合度与阅读顺序排好、截到候选预算后才解析段落数据，重合度改为直接判断两字片段是否出现在原文中（`gram_overlap`，随机 4000 组与原“两字片段集合求交”逐一相等）。合成性能库（`scripts/performance_fixture.py` 默认规模，约 6.4 万段）三次中位数：“社会”183→35 毫秒，“历史”（约 3.2 万段命中）1433→220 毫秒；同库 30 组查询在待补与已建索引两种状态下新旧完整响应 SHA-256 一致。合成库数字，不代表真实书库耗时。测试 `test_only_ranked_rows_are_parsed`、`GramOverlapTest`，各自在换回旧实现时失败。
- 模糊搜索提速（结果不变）：截到候选上限后才解析段落，重合度改为子串判断，不含组合字符的段落改用逐字表做位置映射（`normalization.plain_spans`）。冻结快照新旧交替对照：fuzzy “社会” 4495→773 ms，“国家” 2406→483 ms，长句各类快 11%～27%。1264 组查询的完整响应 SHA-256 与改前一致，全快照 63,994 段的位置映射逐段相等。同日第二轮：两字以下模糊搜索和主题检索的两字扫描改为先只读排序所需的列，截断后再按 rowid 取整行；fuzzy “社会” 再降为 776→288 ms，主题检索 658→195 ms，1384 组完整响应一致。证据见 `reports/fuzzy-search-benchmark-2026-09-30.md` 第七、八节；基线与召回缺口见同报告第二、三节。
- 模糊搜索找回短查询错字（**会改变结果**，经用户批准）：4～8 个字的查询，若错字把每个三字片段都打断、全文索引一条候选都没有，改用两字片段再找一次；三字查询不变，因为大多会返回不相关的“社会X”。冻结快照基准：四字错一字找到 10→14 条（排第 1 的 4→8），五字正中错一字 0→9，六到八字错两字 0→11，找回的高亮大多正好框住原句，无关结果仅小幅增加。代价是这类原本搜不到的查询多约 0.1～0.2 秒。1624 组查询中，结果变化的 330 组都属于这一情形。证据见同报告第九节。
- 证据：`reports/short-query-gram-index-2026-09-29.md`（三方案原型对照与最终验收）；测试 `tests/test_search_short_gram_index.py`。

## 试用中发现并修复

- 书目补全写入时原以导入配置记录为“当前题录”：配置记录不全的旧文献，补一个字段会把配置里缺的书名、作者等连同写空。改为以索引中面板所显示的题录为准，配置有而索引缺的值也保留（先写复现测试 `test_sparse_config_record_never_blanks_values_shown_from_the_index`）。
- MCP 服务器版本号原取契约文件的旧值 0.5.1，改为直接报应用版本。
