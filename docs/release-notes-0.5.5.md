## 更新内容

### 启动守卫:云端占位索引明确报错

- 索引数据库被云盘(如 OneDrive)降级为「仅云端」占位文件时,启动首次读取会等待整份数据库下载,窗口无限停留在加载页。现在启动先检测占位属性,直接给出带操作步骤的错误页(右键文件→「始终保留在此设备」→等待同步完成后重启),不再假死。
- 背景与证据见 `docs/issues/onedrive-placeholder-startup-hang.md`;测试 `tests/test_desktop_backend_cloud_placeholder.py`。

### 章节目录与双语跳转

- 阅读器工具栏新增「目录」，按原有层级展示已入库的一、二级标题，支持方向键、Enter 和 Escape。
- 点击章节高亮左栏标题，右栏按现有对齐关系定位；即使暂停跟随也同步一次，之后保持暂停。没有对应位置时清除旧高亮，保留右栏原位置并说明原因。
- PDF 复用 Markdown 导出的标题可信性校验，EPUB/Word 使用已入库标题样式；不重解析原文件、不生成虚构页码。缺少标题数据的旧文献显示空目录说明。
- 新增只读 `/api/document/outline?source_id=…`；契约与验收见 `docs/issues/reader-chapter-navigation.md`。

### 双语阅读审核修复

- 修复多源分段链接的人工校正在滚动定位时被绕过、过期请求重新打开已关闭对照、新对齐结果未刷新链接缓存三项问题。
- 跟随只移动右栏，不再把左栏拉回搜索命中；定位成功清除旧错误提示。默认仍为左栏驱动右栏，算法与 batch64 不变。
- 回归与真实书库副本的浏览器证据见 `reports/translation-reader-review-2026-09-18.md`。此项修复后已补章节目录，见上节。

### 译本对齐改为按需组件,主程序更小

- 桌面主程序不再打包对齐计算数值栈;安装包体积显著下降(macOS ARM 定向构建实测约减半)。检索、阅读、题录、已有对齐结果与引用定位不受影响,均不依赖该栈。
- 译本对齐的嵌入计算与模型探针改在**独立解释器**中运行;计算源随应用交付,由独立运行时的解释器加载。
- 未安装独立运行时时,译本对齐会**明确显示不可用原因**(而非静默失败或误报);已生成的对照与人工修正保留可用。

### 设置页新增对齐计算组件的安装管理

- 「译本对齐」设置页新增「独立计算运行时」卡片:未安装可**安装**、失败可**重试**、有新版可**升级**、已装可**卸载**,安装/升级/卸载进行中可**取消**;当前有对齐任务在跑时,升级/卸载会显示「任务结束后…」并等待。
- 自带数值栈的老用户(无需单独安装)不受打扰,卡片保持隐藏;精简包缺栈或已装独立运行时时才呈现管理入口。
- **卸载确认如实呈现规则**:卸载会删除运行时及其所属的对齐模型文件,但**文献、已有对齐成果与人工修正都会保留**——不再笼统写「模型保留」。

### MCP sidecar 精简

- MCP sidecar 只读已有对齐、不做对齐计算,不再重复携带数值栈:独立可执行由 77.9 MiB 降到 45.9 MiB(macOS ARM 实测)。这份收益独立于桌面主包——sidecar 是分发包里的第二份数值栈,主包缩小的数字不代表整分发收益。工具行为不变。

### 作品页改版：对齐状态常显，恢复「全部重新对齐」

- 起因：勾选两个版本后才在底部栏显示对齐状态，页面上看不出「对照阅读」依赖「对齐」；旧文献库里换模型后一键「重新对齐已有译本」的按钮在改版中丢失。
- 作品页新增「对照」区，列出每一对版本及其对齐状态（直接对齐 · 已匹配段落 N% · N 处待检查 / 需重新对齐 / 间接关联 / 尚未对齐 · 生成后才能对照阅读 / 生成中 / 等待重新对齐），行内给「对照阅读」与「生成对齐 / 重新对齐 / 生成直接对齐」；含基准版本的对排在前。取代上节的「最多勾选两个版本」与底部对照栏。区底一句说明：对照阅读按对齐结果逐段跟随，对齐由本地模型生成，更换模型后需重新对齐。
- 恢复批量重新对齐：作品列表顶部在存在失效对齐时提示「对齐模型已更换，N 组对齐需重新生成 · 全部重新对齐」，确认后按原对齐方向逐组强制重算，显示进度（i/N 与当前作品、版本对），可「停止」（当前批次结束后停），结束时汇总一次提示。只重跑直接对齐，间接关联随经过的两段直接对齐一并更新。单部作品有 2 组以上失效对齐时，对照区另有「重新对齐 N 组」。作品列表对失效作品标「需重新对齐」。
- 设置里切换对齐模型后，译本对照的状态快照立即失效，回到作品页即显示需重新对齐；提示文案改为指向「全部重新对齐」。
- 「管理版本」抽屉移除与作品页重复的逐对对齐列表，只保留改名、基准、版本名、增删版本与删除作品。
- 真实书库快照副本上走通（15 组失效对齐、4 版本 6 对作品、窄窗口）；批量队列的启动 / 进度 / 停止在浏览器中以模拟任务接口验证，未改动书库。

### 阅读会话状态统一

- 2026-09-20：一次阅读的位置此前散在五处记录（地址栏深链、窗口内的 lastSession、每本书的对照记忆、服务端「上次读到」、作品页缓存），形状各不相同。现在会话记录只有一份定义：左栏、右栏、所属作品、当前位置。
- **刷新或重开独立阅读窗口不再丢右栏**：地址栏深链带上对照版本，开关右栏时地址栏与服务端位置一起更新。
- **关闭阅读器后「继续阅读」立即准确**：阅读器把刚写出的位置直接交回作品页，不再清空缓存后靠 0.4 秒定时器重新查询——那是在赌写入已经落库。
- 恢复优先级写在一处：显式指定（宿主的「继续阅读」）> 地址栏深链 > 窗口内会话 > 每本书的对照记忆。阅读器自己不会擅自跳到上次的位置，跳不跳仍由入口决定。

### 对齐任务的完成刷新统一

- 2026-09-20：作品页和阅读器此前各有一个轮询器盯着同一个后端任务（后端一次只跑一个对齐任务）。同一次生成可能弹两次提示、刷两次视图；反过来，在阅读器里生成的对齐不会立刻更新作品页的逐对状态与「N 处待检查」，要等关掉阅读器。
- 现在监听只有一份：谁先认领任务就由谁负责报告结局，其余各处订阅同一个结束事件。**提示只由发起方给出**，作品页与阅读器都按同一次事件刷新自己的视图。
- 在阅读器里保存校正或「暂不处理」后，作品页的逐对统计立刻失效重算，不再等到关闭阅读器。
- 未改后端接口与任务协议；「生成中 N%」仍未做（worker 没有批次进度来源）。

### 人工校正的读取口径统一

- 2026-09-20：同一条人工校正此前在三处按三套规则读取——阅读器定位有「包含回退 + 过期判定」，逐段「!」标记只认完全一致的选区，作品页的「N 处待检查」既不判过期也不校验目标段。结果是同一条校正在阅读器里已生效、在作品页统计里可能仍被当成没改；重新分段后失效的校正仍被计入「已处理」。
- 现在只有一个读取入口与一条选取规则：有效性（目标分段集一致且目标段仍在）→ 精确选区优先 → 只有阅读器校正可作用于它所包含的选区。MCP 提案保持精确选区语义不变。
- 「待检查」也只有一条判定：算法给出对应但低于置信门槛、两侧都非空、两个方向都没有有效校正。阅读器的「!」改读后端新增的 `needs_review` 字段，与作品页「N 处待检查」保证同一口径。
- 规则与守卫见 [人工校正读取契约](contracts/v0.5.5-alignment-corrections.md)。未改对齐算法、未改已存校正数据，也未新增路由。

### 正文范围检查与修改

- 2026-09-20 复审修复：提交同时校验两本书的分段集，重新解析后的旧段号会被拒绝；编辑一侧保留另一侧目录、输入和滚动位置。起止摘要与设置按钮固定，正文各自滚动。接口见 [正文范围契约](contracts/v0.5.5-body-ranges.md)。
- 起因：对齐质量首先取决于「正文从哪里开始、到哪里结束」识别得对不对。自动识别已修好一类塌缩（见 Bug 修复），但识别错时用户此前没有任何地方能看见和改正。
- 作品页每一对版本新增「正文范围」入口，打开后两本书并排显示，各自有版本名、语言、当前开头与结尾。两边独立浏览、独立修改：改一本不改变另一本的范围，也不改变它的阅读位置。
- 每本书显示真实入库文本段（不重解析源文件、不改原文）。可用目录章节、PDF 页码或文本段序号定位；点选任意文本段只改变「当前选中段」，点「设为开头」或「设为结尾」才改动对应一端。开头与结尾始终显示，可「查看」跳回原文，可「撤销」本次修改。
- 首尾两段都算正文，中间连续纳入；界面显示的结尾即最后一段，提交时换算成库内的半开区间，不漏末段。结尾早于开头时就近报错并禁止提交，不会偷偷移动另一端。
- 底部只有一组操作：「取消」放弃本次草稿（不写入书库），「保存范围并重新对齐」一次提交两个范围并强制重跑**当前这一对版本**。没有单本确认环节，也不要求两本都改过。
- 打开时优先显示适用于当前分段的已保存人工范围，没有才显示自动识别范围。范围按文本段序号记录，绑定这两本书当前的分段数据——重新解析会产生新分段，旧的人工范围不再适用，界面不承诺跨重新解析永久有效。
- 两本书的页码彼此独立，不按页码相等建立对应；没有出版方页码的文献如实显示「页码尚未解析」，用章节与文本段位置定位，不虚构页码。PDF 提供按页跳转，EPUB / Word 走目录与文本段序号。
- 缺少对齐计算组件时仍可打开查看与修改（只读已入库文本），只有提交那一步按真实原因禁用；提交失败或取消时保留本次选择，重开时恢复，可直接重试。
- 新增只读接口 `POST /api/text-alignments/body-range` 与 `GET /api/text-alignments/body-range/segments`；复核范围经 `/api/text-alignments/start` 的 `reviewed_body_ranges` 落入该次运行参数（`body_range_source=reviewed`）。契约与验收见 `docs/issues/alignment-body-range-review.md`。

- 同名归组核对：对照表列出书名、作者、格式、篇幅、页码并标出不一致项，按钮为「不是同一作品 / 稍后 / 归为一部作品」；「不是同一作品」持久记住。
- 统一阅读器：检索、文献库、译本对照进入同一个阅读器，主窗口内占满内容区（不再是大弹窗），应用侧栏收成图标栏、返回时恢复，返回按钮写来源。工具栏：返回、左栏版本下拉、「添加对照版本」（列出其他版本与对齐状态，底部「管理版本…」）或交换 / 右栏版本 / 关闭对照，跟随滚动开关、复制引文、「⋯」（跳到页、在作品中查找、在新窗口打开 / 回到主窗口、显示页眉页脚、管理版本）。原「阅读 | 译本对照」分段切换移除。

- 阅读位置按作品保存版本对与位置，「继续阅读」用 PDF 页序或段落序号如实表述，不冒充印刷页码。

### 译本对照改版：后端存储与接口

- 数据库 schema 升到 v7(附加迁移,只新增表):`document_group_reading_positions`(每部作品上次阅读的版本对与位置,锚点为条目序号 + 码点偏移,不存页码)、`alignment_review_deferrals`(低置信段落「暂不处理」)、`document_group_suggestion_dismissals`(同名归组建议「不是同一作品」)。**v7 库无法再被 0.5.5 之前的版本打开**(旧版会拒绝更高 schema)。

- 对齐计算进程只上报开始与结果,没有批次进度,「生成中」暂不显示百分比。

### 本地 MinerU 不再锁死单一版本：接口自适应 + 可升

- **自部署不再受版本约束**：连接本地 MinerU 时先握手探测接口代数——`GET /v1/health` 通则走 MinerU 4.x 的 `/v1` 作业接口，回落 `GET /health` 则走 3.x 的 `/tasks` 接口。用户自己把本地 MinerU 升级到 4.x，MEFinder 自动切换，不需要等新版本；「检测连接」的提示直接显示握手到的接口代数与版本（如「MinerU 3.x 任务接口 · 3.4.4」）。设置里也可显式锁定 `tasks` / `v1-jobs`，锁定后不静默回落。
- **新增 MinerU 4.x 解析通道**：4.x 用「注册上传 → 流式 PUT 字节 → 完成上传取 file_id → 创建 parse job」取代 3.x 的 multipart 直投 `/tasks`；结果改为下载 `structured_content` 工件。3.x 的 `backend` 名按官方档位模型映射为 tier（`pipeline`→`basic`，各 VLM 后端→`standard`），`parse_method` 映射为 `ocr_mode`。服务端若启用了 API key，可在本地部署设置里配置，按 `Authorization: Bearer` 发送。
- **页码锚点不因换代漂移**：MinerU 4.x 的块坐标是归一化 `0..1`，3.x 是 1000 单位画布。新通道把归一化坐标按 1000 画布换算后入库（与既有文献同坐标系），同时把**精确的归一化坐标**原样带到 `bbox_normalized`，页码识别与引用定位优先用后者，不依赖换算后的取整值。
- **正文入库是印刷原文，不是 Markdown**：MinerU 4.x 交付的块正文是渲染后的 Markdown（粗体 `**`、行内代码、`$…$` 公式、链接与图片、以及对字面 `*_` 等字符的反斜杠转义）。解析适配层会还原为纯正文再入库并据此生成字符区间，否则「劳动是**价值**的实体」这类句子按无标记原句精确匹配会失配、引文里还会带出格式标记。转义过的字面字符原样保留。
- **托管安装器改为「兼容区间 + 取区间内最新」**：清单不再把安装命令写死成固定版本，改为按大版本系列声明安装配方（3.x：`mineru[pipeline]` / `mineru[core,mlx|lmdeploy|vllm]`；4.x：`mineru` / `mineru[torch]`+`mlx-vlm` / `mineru[full]`，以及各自的模型下载参数与配置方式——3.x 的 `MINERU_TOOLS_CONFIG_JSON`、4.x 的 `MINERU_HOME`）。**安装与更新本身**就会先取兼容区间内最新版本作为目标（在后台线程里查，不卡请求；查不到即沿用清单固定版本）；设置页「MEFinder 托管运行时」新增**「检查新版本」**按钮，并如实标明当前安装目标是「兼容区间内最新」还是「清单固定版本」。
- **安装版本按各自回执识别**：已安装组件的识别与启动一律读它自己的 `installed.json`（记录 version / series / config_style），不受当前安装目标影响——装了 4.x 的组件在目标仍是 3.x 时不会被误判成「未安装」，装了 3.x 的组件在目标切到 4.x 后也仍按 3.x 的配置方式启动。旧回执（无 series 字段）一律按 3.x 处理。
- **一次安装只用一份配方**：安装期间的版本、extras、模型下载参数与配置方式在操作开始时冻结；安装进行中调用「检查新版本」不会中途换配方（会明确回答「组件正在操作中，暂不检查新版本」），回执不会写出混版结果。
- **离线仍可装**：PyPI 不可达、返回无法解析或区间内没有更新时，一律回落到清单固定版本（当前 3.4.5），不阻塞安装、不引入必须联网的路径。区间外的大版本（当前 5.x）会明确报「缺少安装配方」，而不是装上去再炸。
- 契约实测依据：MinerU 4.0.4 wheel 的 `mineru/parser/api_server.py`（`APIRouter(prefix="/v1")`，全包无 `/tasks` 路由）与 PyPI 元数据的 extras 清单（4.x 仅 `dev/test/torch/full/all`，`pipeline`/`core` 已移除）。测试 `tests/test_mineru_local_v1_protocol.py`、`tests/test_managed_mineru.py`（含只暴露 `/v1/health` 的假 4.x 服务走完整托管安装—启动—探测）；3.x 通道另在本机 MinerU 3.4.4 上跑通提交—轮询—取结果全链。**尚未用真实 MinerU 4.x 做过端到端解析验收**，4.x 托管安装的 extras 映射与模型落盘路径仍是依据上游元数据的推断。

## Bug 修复
