# MEFinder 素材库局部架构优化计划

2026-11-23 · 三阶段已在工作区实现，未提交。原代码基线 `454eab3` 已合入 `main`（`ce6f79c`）。本计划不改变 0.6.6 的 Windows 实机验收安排。

先改标签读取：用户查一个段落、给一句话加标签，不应随着无关素材的积累而读取越来越多的正文。第二步让 PDF 截图预览的渲染不占用搜索锁。最后仅分出 PDF 框选代码，不重写素材页。三项可以分别验收、分别撤回，不必一起上线。

## 一、先把标签读取限制在当前操作内

**现状。** [搜索结果页](../src/me_finder/static/js/20-search.js)在有命中时异步补标签；窗口重新获得焦点或素材变化时也会刷新。它和[划词标签选择器](../src/me_finder/static/js/22-material-tags.js)都请求完整的 `GET /api/materials`。后端[一次读取五张素材表](../src/me_finder/persistence/materials_store.py)，返回摘录正文、图片元数据和标签关系；不含图片文件本身。这是附加读取，不是检索算法在扫描素材库。

隔离基线：在内存 SQLite 中固定一个标签「实验」，每条模拟摘录含 200 个汉字，均挂同一标签，使用现有仓储和 HTTP 相同的 UTF-8 JSON 编码。1 条摘录时快照为 1,051 字节，1,000 条时为 919,711 字节；两次真正供选择器使用的标签数组都是 20 字节。这是响应正文大小，不是用户机器上的耗时。

**实现。** 保留完整快照及其原有调用方式，素材主页、备份和重建仍可取全量。对高频操作另加两种只读查询，SQL 放在现有素材仓储，复用本地 HTTP 装配和前端请求工具，不加缓存或新依赖：

| 谁在读 | 需要什么 | 不应该读什么 |
|---|---|---|
| 划词加标签；图片导入页没有现成标签时 | 已有标签路径，含父级，排序与现在一致 | 摘录正文、标签对应的所有素材、图片元数据 |
| 搜索结果和右侧「已收集句子」 | 按本次命中的「来源 ID＋段落 ID」去重批量取：该段已收集的文字、起止偏移和标签，供原有展示逻辑核对 | 其他段落、其他文献、图片素材；也不要变成每段一次请求 |

有一个例外：阅读器的批量收集对话框会预勾选**所有选区共有的标签**，不能直接换成只读标签名。第一步保留它原有的读取和预选行为，不把它算作已经优化。搜索补标签继续异步执行；旧请求迟到不能覆盖新查询，标签请求失败也不能吞掉搜索结果。不改 `/api/search`、MCP、数据库结构或摘录身份。

[隔离实测](../reports/materials-scoped-reads-2026-11-23.md)：增加 999 条无关摘录后，标签路径响应仍为 39 字节，固定命中段落的摘录响应仍为 727 字节，二者均逐字节不变。

**验收。**

1. 固定命中段落和标签，再加 999 条属于其他段落、沿用同一标签的摘录。比较改前、改后的响应字节数；改后两种窄查询各自的响应内容和大小都不变。检查实际 SQL：不允许先读完整快照再裁掉字段，批量查询也不能逐段往返。保留固定样本和复跑方法到 `reports/`。
2. 用同一组结果逐项比对：整段标签、局部摘录、同书内不同位置的相同文字、不同书的同名段落、含非 BMP 字符的偏移、无标签和无命中。搜索排序、页码、打开原文的位置不变；旧库缺素材表时只读返回空，不触发迁移。
3. 在浏览器跑一次「搜索 → 划词加标签 → 回到结果 → 打开原文」，再验证独立阅读窗口的标签预选。有新读接口时，同步实际开发版本的 [HTTP 契约](contracts/)及[契约测试](../tests/test_http_api_contract.py)，不改旧版契约。

## 二、让 PDF 截图预览与普通搜索并行

**改前。** [素材控制器](../src/me_finder/materials/controller.py)在 `run_when_ready` 回调内渲染和编码预览。[索引运行时](../src/me_finder/application/index_runtime.py)在回调期间持有搜索也要使用的状态锁，所以在 `get_pixmap` 入口人为暂停后，并发搜索不能在放行前返回。这证明有等待关系，不说明平时会等多少毫秒，也不解释 Windows 启动慢。

**实现。** 在状态锁内取得一致的来源、页码映射和文件标识，锁外渲染及编码。保留数据目录迁移门禁和原有的变更锁，索引发布、其他素材预览和写入仍与渲染串行；这次只解开搜索等待。截图保存的写入事务和去重不变。预览凭据现在绑定来源、物理页和文件版本，不能用同一 PDF 另一页的凭据保存。[并发复现与回归](../reports/materials-pdf-preview-2026-11-23.md)

**验收。** 用事件固定顺序：暂停第一页的渲染，请求一次有已知命中的搜索；**搜索须在渲染放行前返回正确结果**。无超时的暂停事件由测试清理代码保证释放，不能靠假任务自己超时结束。再验证预览后替换原 PDF、渲染中切换来源或重建索引均不会把旧图保存到新来源；旋转页的框选坐标、印刷页码和未校准页的处理与改前一致。若只能通过放松来源一致性或关停保护来消除等待，本阶段不合入，不影响第一项交付。

## 三、分出 PDF 框选模块

[素材页脚本](../src/me_finder/static/js/32-materials.js)在基线版本共 1,283 行；自 v0.6.1 以来有 6 个提交改过它。值得分开的理由是：PDF 选择、翻页、拖框和确认回填已有相对独立的入口 `showPDFCrop(onUse, initial)`，而列表筛选、摘录编辑不需要知道框是怎么拖出来的。

**实现。** [`31-material-pdf-crop.js`](../src/me_finder/static/js/31-material-pdf-crop.js)负责文献选择、翻页、手柄、框选以及预览生命周期，保留入口 `showPDFCrop(onUse, initial)` 与回填参数。下拉控件和图标由素材页注入，不让新模块读取素材页的 DOM。素材主页仍负责列表与详情，图片导入表单仍持有未保存的草稿。未改 CSS、模板、布局、键盘操作或 HTTP 接口。

**验收。** 新模块只装配到主窗口，顺序为标签工具 → PDF 框选 → 素材页。搬移前后对比，除注入图标的调用外，框选函数正文保持一致。[真实浏览器回归](../tests/test_browser_regression.py)覆盖换文献、翻页、框选与整页回填、取消后的草稿和重新打开；特意把第 2 页响应延迟到新的第 1 页预览之后，验证旧响应不会覆盖当前页。在临时测试产物中去掉过期响应判断后，此用例确实失败。

## 实施顺序与停止条件

- [0.6.6 启动报告](../reports/windows-startup-0.6.6-2026-11-23.md)中的 Windows 同机同库启动对照、报告者原摘录粘贴到 Word 的验证仍独立进行。这两项不拿本计划的测试替代。
- 三阶段分别验收。某项未达标，只撤回该项，不迁移用户数据。
- **实施门禁。** 每项按实际涉及范围运行[素材回归](../tests/test_materials.py)、HTTP 契约、Chrome 真实操作；前端有变动再核对 JS 语法与装配指纹。提交前按 [AGENTS.md §3.6](../AGENTS.md) 跑全量 unittest 和 Ruff。只写计划不算实施验收，也不授权提交、打包或发布。
