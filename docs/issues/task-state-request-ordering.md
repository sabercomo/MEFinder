# 组件状态请求乱序：旧轮询覆盖新操作

2026-09-27：设置页四张组件卡片已统一用请求代次防乱序，复现测试先红后绿；导入、对齐任务等其余任务类型尚未梳理。

## 事实

设置页的组件卡片同时有两类请求在改同一份状态：定时轮询（GET）与用户操作（POST 下载、删除、安装、卸载）。两者的响应可能乱序到达。

修复前，四张卡片的保护程度不一：

| 卡片 | 文件 | 修复前 |
|---|---|---|
| 译本对齐模型 | `64-settings-model.js` | 只有轮询之间互相比较代次；下载、删除不参与，在途轮询仍会生效 |
| 对齐计算运行时 | `64-settings-model.js` | 已有代次（操作也递增），逻辑正确，本轮只改为共用实现 |
| 本地 OCR | `70-vision.js` | 无任何保护 |
| 托管 MinerU | `70-vision.js` | 无任何保护；`loadMineruConfig` 带的运行时快照是第三个写入来源 |

复现（`tests/test_task_state_frontend.py`，修复前 4 项失败）：

- 对齐模型：轮询 GET 先发出，随后点「下载安装」；POST 返回「下载中」后，旧 GET 带回「未下载」，界面退回「未下载」，且因为"不在忙"停掉了轮询（`pollsAtEnd: 0`）。后台实际在下载，界面不再刷新。
- 对齐模型：删除后，旧轮询把模型显示回「已下载」。
- 本地 OCR、托管 MinerU：点安装后，旧轮询把状态改回「未安装」并停掉轮询。

## 做法

新增 `static/js/14-task-state.js`（`MEFinderTaskState.createLatest()`）：

- 每次请求前 `begin()` 取代次，响应回来先 `isCurrent(token)`，不是最新就丢弃。
- 用户操作开始时也 `begin()`（或 `invalidate()`），并停掉已排的轮询；操作失败时重新读取，把轮询接上。
- 本地 OCR「保存设置」只在保存成功后作废在途轮询，失败时轮询照常。
- `loadMineruConfig` 与托管轮询共用代次：旧快照只更新表单，不改运行时卡片；读取失败且运行时仍忙时重新接上轮询。

## 推断（未验证）

- 同类问题可能存在于导入队列、对齐任务、Zotero 同步等其他轮询处，本轮未逐一审查。
- 请求代次只解决"同一窗口内乱序"；主窗口与独立阅读窗口之间的状态同步不在此范围。
