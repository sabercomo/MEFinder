# 切换同步书库后已下载组件不可见

## 2026-09-13：事实与修复

- 事实：当前桌面数据位置指向 OneDrive；原实现把 OCR 配置、安装目录和对齐模型缓存全部跟随书库 runtime。共享 OCR 配置含 Windows 绝对路径，在 macOS 校验时使整份设置读取失败。
- 事实：本机 Application Support 中两个 OCR 安装仍完整，两个模型预检通过；共享目录两个模型预检不通过。修复前的单元复现明确显示 OCR 配置解析仍指向切换后的书库。
- 推断：用户提供的分析把共享模型损坏归因于同步软件破坏符号链接；本轮未独立证明具体破坏过程，不将其记为确定根因。
- 修复：当前 macOS 桌面书库的 OCR 配置、OCR 安装/卸载和对齐模型管理/计算统一解析到稳定本机目录（macOS Application Support），忽略书库位置指针。显式开发/测试 runtime 保留隔离路径；不搬动文献库，不修改或删除共享组件。
- 验证：`tests.test_component_runtime_location` 覆盖切换书库后的配置/安装/管理/默认计算路径及实际任务入口的预检与计算路径一致性、Windows 既有路径兼容与开发隔离。本机两个 OCR 的 `--help` 成功；两个模型 `local_files_only=True` 实际推理成功，输出形状分别为 `(1, 384)` 和 `(1, 1024)`。

- 最终门禁：只含本次补丁的隔离工作树全量 2229 项 unittest 通过（22 跳过），Ruff 通过。原工作区另有未提交前端改动导致装配指纹失败，本轮未修改其基线。

## 范围与限制

本轮复用本机已有完整安装，不自动迁移仅存于共享目录的旧组件（虚拟环境包含绝对路径，不能直接搬迁），不修复共享目录的 Windows 安装或缓存。Windows 组件路径、MinerU、组件目录清单和便携/显式自定义 runtime 不在本次改动范围。现有桌面安装包尚未包含此次源码修复，需重建后生效。
