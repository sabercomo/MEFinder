# 短词检索的三个待办(2026-09-29 从 `search_passages` 两字查询修复中分出)

本轮只修了「两字查询在 SQLite 库上返回空」这一处缺陷(`search_recall_passages._sql_scan_passages`,复现测试 `tests/test_search_passages_short_query.py`)。下面三件与它同源但性质不同,刻意没有混进同一次改动。

## 1. 慢查询会拖住下一次搜索

- 事实:一次全库短词查询要把候选段落逐段切词、算重合度、排序后才取前 64 段(`search_recall._sql_fuzzy_pass` 的非 FTS 分支)。真实库上 fuzzy 模式搜常见短词仍慢,已记在 `docs/release-notes-0.5.8.md`「检索:两字短词提速」的已知遗留里。
- 事实:请求路径上没有取消机制,前一次查询跑完之前,后一次搜索只能等。
- 推断:这条与模糊打分算法本身无关,牵涉的是在跑的查询怎么中断(连接层取消 / 分批让出 / 前端丢弃过期响应),应单独立项,不要和召回质量的改动绑在一起。

## 2. 短词召回质量基准:召回与噪音必须一起量

- 事实:三字查询只切出一个三字片段,所以「社会论」在库里找不到「社会学」——候选阶段就是空的,评分函数根本没被调用(`search_scoring.best_window_ratio` 未被触达)。
- 事实:两字查询只切出一个两字片段,每条命中的重合度都相同,结果只按阅读顺序(文献、段落序号)排列,不是相关性排序。这与旧的内存后端行为一致。
- 事实:单字查询在 SQLite 与内存两种后端上都返回空。本轮未改。
- 推断:若为找回「社会学」而放宽三字查询的候选范围,「社会」这类高频词会把结果淹没——0.667 刚过 0.58 的模糊门槛,说明短词门槛本身偏松。所以基准要同时量两件事:**该找到的原句有没有进候选**,以及**返回了多少不相关段落**。短词要不要放宽,由这两个数一起决定,不能只看前者。
- 做法约束:AGENTS.md §0 原则 5——涉及阈值与准确率的结论必须引用 `reports/` 实证报告,不得凭感觉调参。基准建好后落在 `reports/`,本文件只引用。

## 3. 一个可能更省事的优化(待基准证明)

- 推断:查询在原文里能原样找到时(`best_window_ratio` 走 `query_plain in plain` 的早返回,给 0.91),模糊模式或许可以直接采用精确命中的结果,不必把所有候选读出来再排一遍。
- 约束:这可能改变结果排序。没有基准证明「完整响应逐字段一致」之前不动手;比对方法参照 `reports/search-acceptance-round2-2026-09-13.md` 的隔离 A/B(`git worktree` 独立检出旧版,同一冻结快照,逐字段 digest 比对)。

## 2026-09-29 复审补充与更正

- 事实：原先的预筛等价测试建库后有 6 条待补、0 条已索引记录，不能证明建好索引后的预筛正确。已补成真正排空待补后比较完整响应，并覆盖更新/删除待补与 64/65 候选预算边界；故意破坏预筛时，原测试通过、补强后的测试失败。产品查询实现无需改动。证据见 `reports/short-query-gram-index-2026-09-29.md` 第七节。
- 更正上文“单字查询两种后端都返回空”：查询与段落都使用两字片段；单字查询通常无法召回长段落，但归一化整段恰好就是该单字时可以命中。已复现 SQLite 库中只有“社”的段落用 `search_passages("社")` 返回 1 条。本轮保留既有行为，不扩展单字召回。
- 更正上文“与旧的内存后端行为一致”：两字命中的重合度都相同这一点一致，但同分次序不同。SQLite 显式按文献、段落序号、段落 ID 排；内存后端保留输入列表次序，不能假定跨后端结果顺序相同。
- 推断边界：0.667 高于 0.58 只能证明该样本在现有评分门槛之上，不能单凭这个数断言短词门槛过松；阈值和噪音结论仍须由标注基准支持。
- 优化边界：直接采用精确搜索的完整响应会改变 `match_type`、分数、候选预算与排序，不能当成透明替换。可以研究复用候选查找，但须保留模糊搜索契约并通过逐字段比较。
