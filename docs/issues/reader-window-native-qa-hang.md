## 2026-09-10 — 捕获关闭回执死锁并修复

**事实**：GLM 留下的 `native_qa2.log` 抓到非 daemon 的 `_call` 线程停在
`webview/util.py:264 → Window.evaluate_js → cocoa.py:916 → Semaphore.acquire`，
主线程停在 `threading._shutdown`。测试宿主已经完成服务与数据库清理。
本轮用入库驱动 `tests/native_reader_window_probe.py --legacy-close` 再次复现同一栈；
30 秒输出线程栈，35 秒仍未退出，由父进程终止本次隔离测试子进程。

**原因**：原 `close_reader()` 是普通 JS API。Python 处理器先调 `destroy()`，
随后 pywebview 仍通过 `evaluate_js` 回传返回值。窗口先被销毁时，WKWebView 回调不能完成，
桥接线程永久等待，阻止解释器退出。这证实了“GUI 循环返回后进程残留”这一具体路径；
此前另一次无栈的彩虹转圈是否完全相同，仍不能单凭现有证据认定。

**修复**：删除关闭 API，使用当前固定版本 pywebview 6.2.1 的公开窗口状态通知。
页面设置 `readerClosed = true`，Python 订阅后销毁该窗口；JS 发起的状态变更不回传 JS 结果。
没有采用固定 0.5 秒延迟或产品侧 `os._exit(0)`，没有修改安装的 pywebview。

**验证**：新增测试先失败再通过；真实 bridge 分发测试确认关闭不调用 `evaluate_js/run_js`。
旧路径超时的同一原生场景，修复路径连续 3 次自然退出（退出码 0）；
进一步验证了默认弹层、两窗口锚点和对照状态隔离、移动缩放、正文填满窗口、重开与主窗口带子窗口关闭。
本轮所有原生窗口隐藏、不获取焦点，只用临时测试库。详情及边界见
`reports/reader-window-validation-2026-09-10.md` 后续记录。
