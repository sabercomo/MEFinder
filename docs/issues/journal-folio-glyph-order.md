# 期刊论文页码：页脚数字被反序存储，自动识别读不出

2026-11-01 立项并在 0.6.1 开发线修复（新导入与「自动识别」生效；本机库已按同一路径对 85 本应用）。

## 事实

- 本机库 430 本 PDF 中 121 本页码未校准，其中 119 本是 40 页以内的期刊论文（只读统计 `pdf_page_mappings.method == "uncalibrated"`）。
- 抽查原 PDF 页边：页码确实印在页上，但文字层把每个数字存成独立的文字对象，且按从右到左的顺序写入。例：孙亮 2016（刊印 pp.16—22）PDF 第 1 页页脚依次是 `6`（x=72.2）、`1`（x=67.0）；曾誉铭、关韶华 2020（pp.25—40）为全角 `· ５ ２ ·`，同样反序。按横坐标重排即得 16、25。
- 旧逻辑按文字流读块文本：拆成 6 和 1 两个候选，或读成 61、52，连不成 +1 序列；页脚脚注编号 1、2、3 反而形成短序列。多数文章因此未校准，另有 11 本被自动应用了“1、2、3”这样的错误页码（如李和佳 2011 刊印 pp.90—94，库内显示 1—4）。
- 少数文章文字层为私有区乱码字形（如蓝江 2018），读不出数字，只能靠 OCR/MinerU，本次不处理。
- 更正：此前对话中曾据“孙海洋 2019 题录 12-21、页面印 126”推断题录页码不可靠，实为取错了文件（同作者同年另一篇《当代批判理论新趋势》）；该文实际印 pp.12—21，与题录一致。题录页码仍只作核对，不作页码来源。

## 修复

- `pdf/auto_page_mapping.extract_native_pdf_glyph_run_candidates(path)`：在页面上下 `edge_ratio` 带内读 PyMuPDF `rawdict` 字形，按基线分行、按横坐标排序，取独立成段（只允许 `·`、`—` 等装饰相邻，两侧留出 1.2 个字号空白）的 2—4 位数字串，且须同时满足：
  - 文字流顺序与视觉顺序不一致——文字流正常的 PDF 不产生任何新候选，结果与改前完全相同；
  - 字号一致（相差不超过 10%），相邻数字起点间距不小于字号的 25%——排除 OCR 版扫描书两层文字叠放（《马恩文集》(OCR) 每个页码数字存两份，不排除会读出“1100”“44”）。不比较字框重叠：全角数字的字框天然互相重叠。
  - 年份（1800—2099）与圈码脚注（①，非十进制数字）排除。
- 候选来源仍记为 `native_pdf_edge_text`，映射方法仍是 `native_pdf_edge_sequence`，前端与页码说明无需新增枚举；得分 0.92，高于同页块文本误读（0.82/0.90），低于竖排合并汉字页码（0.96）。`page_mapping_service.PageMappingService.infer` 把它并入页边候选。
- `pdf/page_refresh.refresh_page_text` 新增 `renumber`（CLI `--renumber <source_file_id>`）：点名的书允许按现行导入规则改引用页码，同时换用新的映射记录与 PDF profile，书名、书目等其余记录仍原样保留。用于用户确认后刷新科尔施《马克思主义和哲学》。
- 测试：`tests.test_auto_page_mapping.GlyphOrderFolioTests`（反序页码端到端得 16—21 高置信、全角装饰、脚注/期号/年份不算、文字流正常不介入、双层叠放与两层不同字号不拼接）；`tests.test_pdf_page_refresh.test_named_book_takes_the_current_citation_pages_and_mapping`。排序、文字流顺序、起点间距、字号四条规则各做过变异检查，去掉任一条都有用例失败。

见 [reports/journal-folio-glyph-order-2026-11-01.md](../../reports/journal-folio-glyph-order-2026-11-01.md)：全库开/关对比 333 本逐页相同，85 本变化中 79 本与题录逐页吻合、6 本无题录经人工核对，其他 0 本。
